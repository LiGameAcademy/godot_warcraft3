## 2. 为什么重构

旧流程主要把 MDX 转成 glTF，再经 Godot 烘焙 SCN。成功写出场景不等于恢复了源资产语义：多层材质、队色、动画显隐、粒子、Ribbon、billboard、挂点和肖像机位都可能丢失或被近似处理。游戏还有旧资源启发式修补，查看器与游戏的结果可能不同。

最终发布目标要求玩家只提供经典魔兽原版安装目录；玩家不应自行安装 Godot 编辑器、Node 或 Python。因此开发工具、随包源解析运行时、游戏内编译和缓存挂载必须形成可验证的完整流程。

范围先以 Echo Isles 开发地图及相关建造、训练、技能、物品和 UI 资产为准。接受缓存重建，优先自动化；未支持字段、缺失依赖与近似实现必须有诊断。查看器和游戏均验收，以游戏内表现为最终依据。

## 3. 最终工作流与边界

经典 MPQ 目录（只读） → Warcraft 适配器 → Model IR、glTF、依赖与来源证据 → Godot 编译 worker → 可重载 SCN 和编译报告 → 内容/场景校验 → 原子安装路径表与内容根 → 持久索引 → 下次启动校验并恢复。

- 适配器边界为后续输入格式留出接入位置；不代表所有格式、CASC 或全部原作资产已支持。
- JS 负责源解析与任务准备，Godot/GDScript 负责引擎场景编译。没有强行将整个 SCN 编译过程重写为独立 JS。
- Windows 发布包携带 Node 与适配器；同一个游戏 EXE 通过 headless 工作模式编译场景。玩家无需本地 Godot 编辑器。
- 源文件不写回，运行资产走缓存；内容签名、编译签名、依赖和诊断可追踪。
- 缓存使用独立版本发布、完整哈希验证、写锁和活动读者标记；支持取消、重试、异常退出恢复及显式维护。
- “保真基座、可选增强”是产品方向。当前部分特效为近似或重构呈现，不能将未分离产物包装成两套已完成 profile。

详细契约与历史批次见 [路线图](../design/asset-convert/RUNTIME_IMPORT_REBUILD_ROADMAP.md)、[玩家端导入](../design/asset-convert/PLAYER_SOURCE_IMPORT.md)和[收尾验收](../design/asset-convert/ASSET_PIPELINE_CLOSEOUT.md)。

## 4. 本次完成的主要工作

### 审计、清单与编译

建立全量特征审计、问题分级、依赖与运行时资产引用收集、开发地图清单和源资产恢复。定义覆盖规则统一进入地图目录、建造、科技、命令卡及物品；避免只扫模型纹理却漏掉 pathTex、地形、图标等实际游戏依赖。

引入 IR、bake 任务、无状态编译 worker、独立进程保存/重载验证与缓存签名失效。通过真实 Footman 和代表特效验证，逐步接入完整开发地图与发布游戏，而不是停在开发工具成功输出文件。

### 只读资产查看器

独立查看器用于批量筛选、诊断和运行时预览，服务未来替换自有资产；Warcraft 原始格式解析留在适配器中。它不编辑节点、不重新 bake、不保存资源，也不替代 Godot 的场景制作职责。

本轮增加目录树/列表切换、只读节点树、动画元数据、可收起诊断面板、30 FPS 当前帧/最大帧与定位、实例级循环开关、重播/暂停、相机重置与适应模型、坐标轴及标准视图、玩家颜色与实际加载路径。修正缺少有效环境补光造成的黑暗预览。

帧定位不是粒子历史倒放；重播通过重建实例清理历史。查看器不承担原作视觉是否正确的最终裁定。使用入口见 [查看器 README](../../apps/asset_viewer/README.md)。

### 特效与游戏表现

- 粒子、拖带、billboard、源采样与动画控制语义进入编译链；使用牧师投射物、大法师火球、英雄光晕及 Ribbon 样本回归。
- 补齐多层队色与内嵌 Shader 的游戏适配，实例修改材质时隔离资源；中立单位遵循源颜色和固定 UnitUI 覆盖。
- 肖像背景板按源语义标记，在战场/HUD 实例中屏蔽；源 Camera 与 Portrait 序列用于肖像构图。
- 修正建筑 Stand 显隐、主城等级和脚手架；补齐 pathTex，分别处理禁建与禁行通道。
- 接入水元素模型和相关技能资产，修复出生/一次性施法结束、暴风雪持续施法、普通攻击收招及 Weapon Ref 火球出生位置。
- 建筑死亡按 Death、尸体衰减和独立贴花生命周期处理，不让粒子片长决定游戏规则。
- 补齐辉煌光环受益单位脚底提示，改善暴风雪、群体传送预览和实际效果的可见度。

原因、参数边界和手动步骤见 [游戏内复验](../design/asset-convert/GAME_ASSET_REVIEW.md)及[代表特效验收](../design/asset-convert/FX_SAMPLE_ACCEPTANCE.md)。这些修复不等于所有特效已与原作逐帧一致。

### 启动、性能与最后两项修复

缓存哈希移入后台，增加文件数、读取量、耗时和取消状态，处理晚取消与关闭窗口竞态。首次读取与运行长帧仍按实测单独记录，不能用热缓存成绩承诺冷启动时间。

#27 去掉编辑器绕过缓存向导的默认路径，记忆本机原版、缓存和编辑器运行时目录；命令行显式参数优先。编辑器 worker 显式指定工程目录，发布包仍使用其旁边的运行时。

#28 修复源 `source_looping=false` 与持续砍树状态的冲突：采集状态不会每挥一次斧头就重播，因而 Attack Lumber/Gold 需要显式循环；普通战斗 Attack、出生和一次性施法保持各自策略。循环修改不污染其他实例或模板。

## 6. 归档后如何启动与排查

在仓库根同步共享源码后，打开 `apps/game/project.godot`，用 F5 从主场景启动。有效缓存自动进入；缺失、损坏或编译签名过期会停留资源向导，不自动回退旧模型。

向导三个输入框依次是：

1. 经典魔兽原版目录：包含 MPQ。
2. 缓存根目录：包含管线索引和场景产物；默认 `user://wc3-cache/source-import`。
3. 编辑器导入运行时目录：包含 `node.exe`、`runtime-bundle.json` 的 `asset-import-runtime`，不能填缓存目录。

填写后点击“检查此缓存”；不兼容时重新导入。本机记忆在 `user://asset_import.cfg`，不要把机器绝对路径提交为项目默认值。第三框仅用于编辑器，发布游戏使用随包运行时。

本机历史验收包的配套报告是 `tools/asset-convert/tmp/issue-26-7167ce45/report.json`，记录 binary、cacheRoot 与运行时代码提交。它包含 #28 的运行时代码，但不包含后来全部主干更新，也不包含 #27。它是历史复验样本，不是当前主干发行包。

尤其不要再用 `development-9beFl2/release/game.exe` 验收新代码：它是 10 月 7 日旧导出。切 Git 分支、合并 PR 或同步 packages 均不会更新已经导出的 EXE/PCK。更新发布包时必须重新导出，并核对对应报告、程序路径和缓存签名；过期缓存重新导入，不修改签名绕过检查。

旧会话中的仓库路径已迁移。以后从当前 checkout 定位工程，不硬编码旧目录。日常说明见 [游戏 README](../../apps/game/README.md)。
