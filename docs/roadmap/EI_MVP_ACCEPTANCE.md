# EI 1v1 MVP：当前目标与验收

日期：2026-09-13。依据用户最新目标，本文件取代此前“完整四族、编辑器、战役”作为当前交付范围。旧路线图保留为历史背景。本文件是验收约定，未勾选的项目不代表完成。

## 交付目标

在 Godot 4 中运行经典 EI（Echo Isles）双出生点对战，玩家使用完整操作界面与对手AI打一场可结束、可重新开始的对局。先用当前人族实现验证十个系统的协作；种族覆盖必须随版本明确列出，不能据此称为四族完成。编辑器、战役、联机服务不作为本轮MVP的完成门槛。

资产、对象数据和游戏常量必须来自同一可追溯基准；本地补丁来源已开始统一，但版本兼容与所有原版机制一致性尚未证明。修复原版BUG、修改不良设计和新功能应各有触发案例、理由、预期行为与回归证据，避免把缺失机制当作设计改进。

## 十个系统的可观察成果

| 编号 | 系统 | 必须演示并验证的行为 |
|---|---|---|
| EI-01 | 地图初始化 | 正确加载地形、路径阻挡、金矿、树木、野怪营地、掉落配置、中立商店和双方出生点；玩家归属、初始资源与人口正确；加载失败可诊断 |
| EI-02 | 建造 | 预览与合法性反馈；拒绝阻挡/资源不足的摆放；工人到场施工、进度、完工、取消与退款；未完工建筑交互和被摧毁处理正确 |
| EI-03 | 单位 | 正常付费训练、队列与取消、人口占用/释放、集结点；编队建立/召回；单位自主索敌、追击、回位与待命行为一致 |
| EI-04 | 移动 | 单位绕开地形和建筑，群体移动不长期堵死；编队目标分配合理；移动中可改令、停止；狭道、转角和动态障碍有固定复现场景 |
| EI-05 | 战斗 | 攻击命中与冷却、护甲与伤害类型、技能伤害/治疗/状态、投射物、死亡清理、经验与掉落；同次死亡只结算一次 |
| EI-06 | 道具 | 六格背包、拾取/丢弃/交换/使用/出售、次数和冷却、技能联动；地图掉落表和商店库存/价格正确；死亡复活后的保留规则正确 |
| EI-07 | 英雄 | 祭坛训练与复活，经验阈值、等级属性、技能点与学习条件；正常战斗升级，界面同步；复活费用、时间、生命/魔法及背包符合所选基准 |
| EI-08 | 指挥官 | 点选、框选、多选、主选与编队；右键按目标类型移动/采集/攻击/交付/拾取；追加指令、停止和失效目标处理；操作不控制敌方单位 |
| EI-09 | 对手AI | 从正常初始资源采集、造供给/军营/祭坛、训练与组军、清野、进攻和必要防守；能摧毁基地触发结算；不依赖测试赠兵或补资源 |
| EI-10 | 资源采集 | 金矿与木材容量、工人采集/携带/交付、采集点枯竭、交付建筑丢失后的重选；不同玩家库存、花费与退款严格隔离 |

以上每项保留纯规则测试、组件测试、真实地图集成及人工操作证据的区别。数据行存在、模拟下单和直接扣血夹具不能替代正常经营验收。

## 完整对局门槛

- [ ] 从正常开局经采集、建造、训练、清野、升级与学习技能、物品使用/出售、英雄阵亡和付费复活，到敌方基地摧毁及唯一胜负结算。
- [ ] 交换双方出生点验证；连续通过结算界面重新开局三次，资源、队伍、英雄登记和控制器无旧局残留。
- [ ] 操作链覆盖十个系统，运行日志没有未解决的引擎ERROR、崩溃、重复结算或永久卡死。
- [ ] 独立干净启动可按说明准备本地资源并运行；明确MVP种族、技能、物品和AI能力范围以及已知限制。

当前自然自动对局只验证部分经营/进攻/结算，新增自然经验及升级断言仍在验证中。它不覆盖全部背包交互、复活、编队和人工操作，所以不能据此关闭MVP。

## 工程与性能门槛

- 数据与表现分离；对象定义、价格、技能配置、掉落和AI构建选择尽量读数据。组件负责各自生命周期，跨系统通过命令、结果或事件协作；增加规则不应继续把所有实现堆入GameDirector。
- 日志至少支持DEBUG/INFO/WARN/ERROR和系统分层过滤；关键失败保留单位/玩家/目标、资源变化和场景上下文。频繁日志可关闭，错误不得被测试PASS掩盖。
- 性能记录必须注明机器、Godot版本、渲染方式、地图、单位数与运行时长。已有性能面板不能替代采样报告；需记录帧时间分位数、物理耗时、寻路耗时/请求数、节点与内存趋势、绘制调用、加载时间。
- 先在正常EI对局及逐级增兵压力场景采样，再制定基准机预算。无基准数据时不虚构FPS达标；修复前后用同一剧本比较，记录卡顿和长期增长。
- C++/GDExtension仅在剖析证明某热点值得迁移后引入，并保留接口和结果一致性测试；不以重写语言代替定位瓶颈。

## 小里程碑与Git提交

1. **范围与证据基线**：本验收表、当前数据来源、测试分类和已知缺口可审阅后提交文档检查点。
2. **核心规则闭环**：死亡/经验/背包/复活等每个可独立验证的修复，相关测试及错误检查通过后提交；未通过的错误继续登记，不能以“功能断言通过”标完成。
3. **EI操作闭环**：正常对局覆盖十系统、交互与重开证据齐全后提交。
4. **性能与可复现交付**：完成基准采样、必要热点优化、启动说明与回归后提交MVP版本。

每次提交仅包含该里程碑相关代码、测试、文档；核对暂存差异，保护已有未提交工作，不混入本地游戏资产。提交说明写明行为变化、验证与剩余限制。已有大量工作区改动不因为新要求而一次性打包成“全部完成”。
