# RTS 内核重构开发路线图

日期：2026-09-27（计划定稿）；状态更新 2026-09-28：M0 工具链验证（部分）+ M1 双宿主骨架最小形态**已落地**——见 `docs/verification/rts_kernel/M0/R00.5_asbuilt.md`。M2 真实移动与之后均未开始；本文完成仍不代表实现完成，文档与代码仍按 §11 工作包规则同步。

设计依据：[内核契约](../architecture/RTS_KERNEL.md)、[迁移与验收](../architecture/RTS_KERNEL_MIGRATION.md)、[技能系统](../architecture/RTS_ABILITY_SYSTEM.md)。本文细化执行顺序与工作包，不替代上述约束。

## 1. 路线与交付边界

先证明纯 C# 模拟能独立运行、能接入当前 Godot、能保存并恢复，再逐条替换玩法链。每个里程碑同时交付内核行为、必要的表现接入、自动验证及迁移记录，不把 UI 接入、快照和旧代码清理全部推到最后。

路线：M0 基线 → M1 双宿主骨架 → M2 移动 → M3 战斗 → M4 经济生产 → M5 技能英雄物品 → M6 完整对局 → M7 默认切换与收尾。

与原迁移批次的对应：M0 是前置准备；M1–M3 对应 Batch 1；M4 对应 Batch 2；M5 对应 Batch 3；M6–M7 对应 Batch 4。没有扩大游戏功能范围。

规模基线：最多 10 玩家、常规 300/压力 500 活跃单位。人口不直接推导实体上限；建筑、召唤物、资源节点、物品、Buff 和弹道分别统计。Windows 优先、普通 .NET 内核、单线程固定步长、永久不引入 ECS 框架。

不在本路线交付：联机收发/命令帧调度、预测回滚、跨平台确定性、战争迷雾、独立通用插件、技能编辑器、配置热更新与继承、跨版本存档、完整资源管线重写。

## 3. M1 — 纯 C# 骨架与双宿主接入

**成果：一个实体由同一个内核驱动，可在 CLI 和 Godot 中运行。依赖：G0。**

- [x] R01.1 创建普通 .NET 类库、CLI 与测试工程；内核锁定 net8，当前 PC 的宿主锁定 net10。`check_kernel_layout.py` 检查直接及传递 Godot 依赖，负面夹具已验证。
- [x] R01.2 实现首版对局实例、EntityId、最小状态、命令接收/执行结果、固定 Step、稳定随机流与事件身份。
- [x] R01.3 实现最小帧快照、恢复、规范化校验与字段级首差异报告；覆盖下一 ID、随机流和已接受未执行命令。
- [x] R01.4 创建集中 Godot C# 桥接；隔离场景由 GDScript 提交生成、速度和停止命令，节点只消费批量位置镜像，无模型时仍能推进。验证记录见 `docs/verification/rts_kernel/M1/GODOT_BRIDGE.md`。
- [x] R01.5 两个 Godot 对局实例交错推进、以不同批次执行同一输入并收敛；销毁桥接后由快照重建无残留。`Test-GodotKernelBridge.ps1` 提供可重复构建/测试入口。

**退出门 G1：** CLI 不加载 Godot 即可运行；Godot/CLI 相同初始数据和输入产生相同状态；销毁实例后恢复可继续；C# 与 GDScript 桥接不会逐属性暴露可变内核对象。

此时只允许最小测试位置推进，不把它称为完成寻路或真实移动。主游戏保持原入口，新入口只供隔离验证。

## 4. M2 — 真实移动、地图查询与导航

**成果：玩家选中单位后下达移动命令，由纯 C# 完成移动全过程。依赖：G1。**

- [ ] R02.1 转换现有地图可走性、高度、静态障碍、出生点与单位移动参数；保留现有解析和资产加载流程。
- [ ] R02.2 实现纯 C# 路径查询与稳定同代价排序，对照现有 PathQuery/AStarGrid2D 和脚本 A*；首轮同步处理，禁止墙钟预算影响规则。
- [ ] R02.3 迁移路径跟随、转向减速、坡度、预约、局部避让、群体落点及当前编队规则；停止/替换/排队命令接入统一订单语义。
- [ ] R02.4 接入选择与移动表现，保留 Godot 模型动画与插值；位置/朝向由内核独占，移除已切换实体的旧移动写入口。
- [ ] R02.5 测试窄路、斜坡、卡边、不可达、大尺寸单位、拥挤与动态障碍；移动中恢复快照，比较后续路径推进状态。

**退出门 G2：** 不穿墙、尺寸/占地规则成立；允许等价路线拐点不同；300/500 移动场景有实测。30 Hz、数值精度、转向手感形成明确结论，问题先修复或调整设计，再进入扩大迁移。

建筑系统尚未迁移时，以测试命令驱动动态障碍验证；不宣称实际建造闭环已完成。主游戏接入如遇未迁移控制器反写，则保留隔离场景而不双写。

## 5. M3 — 攻击、弹道、死亡与首个完整验证闭环

**成果：移动 → 自动索敌/攻击 → 弹道 → 伤害 → 死亡，在两种宿主中一致。依赖：G2。**

- [ ] R03.1 迁移生命、攻击参数、射程、前摇/冷却、追击、攻击移动/坚守与相应单位自动行为，保持已有模式与优先级。
- [ ] R03.2 迁移伤害、逻辑弹道、目标失效、击杀与实体移除；尸体和视觉弹道独立，不以动画回调决定结算。
- [ ] R03.3 接入生命条、攻击动画、受击反馈、死亡与选择失效；视图读取不能反向写入生命状态。
- [ ] R03.4 固定同帧时序：双方致命攻击、目标中途死亡、新实体何时参与模拟、状态清理与事件顺序；记录必要行为差异。
- [ ] R03.5 前摇中/弹道飞行中快照恢复；从命令日志重放，逐帧比较校验；300/500 混战性能验证，冻结内核与桥接预算。

**退出门 G3（首个大门）：** 无 Godot 的移动战斗闭环、Godot 可操作场景、快照、重放、实例隔离全部通过。明确寻路质量、时序与性能风险可控后，才规模迁移其他玩法。

如果未通过：修当前闭环，不绕过门槛开发通用技能框架，不退回“内核端口返回 Godot 控制器”。

## 6. M4 — 采集、建造、生产与经济 AI

**成果：农民采集 → 交付资源 → 建造 → 训练 → 新单位行动。依赖：G3。**

- [ ] R04.1 库存、人口、支付/退款事务及可诊断结果；同帧争用资源不超支，失败无部分提交。
- [ ] R04.2 采金、伐木、携带、交付、资源耗尽、进矿/施工在场性与导航规则联动。
- [ ] R04.3 放置校验、清场、动态占地、工地生命/施工、取消和建筑破坏；预览仍在 Godot，最终校验在内核。
- [ ] R04.4 训练/队列取消、生成出口、集结点及已实现科技；人口预留与释放跟随真实生命周期。
- [ ] R04.5 对应经济 AI 使用正常命令；接入库存、人口、建造与生产 HUD，测试各阶段快照恢复和连续经营。

**退出门 G4：** 经营闭环可交互也可无人值守推进；生产、建造、采集中的恢复不重复扣费、不丢人口、不遗留阻挡；经济 AI 不直接修改状态。

民兵等形态变化先保留明确接缝，需依赖技能/属性系统的完整行为在 M5 收口；不能因中间批次尚未支持而在主游戏静默删除。

## 7. M5 — 精简 AbilitySystem、英雄与物品

按以下小闭环执行，避免先开发一个功能庞大但没有实际技能的框架：

- [ ] R05.1 统一目标过滤、法力、效果结果和属性修正入口；先迁移治疗，验证费用、失败、冷却、UI 与读档。
- [ ] R05.2 迁移弹道眩晕技能，补目标弹道模板、状态实例、持续时间、叠加/刷新及目标死亡处理；普通攻击与技能共用结算。
- [ ] R05.3 增加 JSON 加载、Schema 与语义校验、默认值归一化及内容哈希；旧内容转换器输出同一契约。通过治疗/弹道示例验证，无重复 ID、继承、合并或热更新。
- [ ] R05.4 用暴风雪落实引导/周期效果、取消与显式运行进度；迁移召唤和传送，以真实需求增加专用 C# 行为。
- [ ] R05.5 迁移剩余主动、开关、被动、光环、自动施法，补 Buff/属性修正顺序与形态规则。逐技能维护行为与测试映射。
- [ ] R05.6 迁移英雄成长/技能等级、既有复活、背包/商店/掉落/物品次数；普通攻击和物品保留自己的流程。
- [ ] R05.7 接入技能卡、英雄与物品 HUD；交付参数修改、效果组合、自定义行为三类教程和可运行示例。

**退出门 G5：** 当前技能清单全部覆盖，多级数值、引导、被动、Buff、召唤及物品中途恢复一致；JSON 结构与语义错误能定位；新机制可以用局部 C# 扩展而不修改万能分发器。

旧 AbilitySystem 先解除本游戏模拟依赖，完整引用清理后再删除不再使用部分；不要求维护两个语言版本。效果组合顺序、中断退款、Buff 刷新等不得因“简化”而擅自改变。

- [ ] R07.2 扫描源码、场景、资源、Autoload、测试与各应用引用，清理不再使用插件；不误删其他用途。
- [ ] R07.3 在冻结基线机器上执行 300/500 活跃单位移动、混战、经营压力场景，报告附属实体、逻辑耗时/分配与 Godot 帧时间。
- [ ] R07.4 验证 Windows 发布制品、共享包同步、地图编辑器原有流程及无开发目录依赖启动。
- [ ] R07.5 交付最终验收记录、测试映射、快照/回放使用说明和剩余玩法改进 TODO；将历史入口明确标记退役。

**退出门 G7：** 全部既有范围回归通过、无双状态权威、无内核 Godot 依赖、同环境重放/恢复一致、性能达冻结门槛。未实现的未来联机和迷雾不能作为已支持能力宣传。

本轮结束后才单独安排玩法优化、未来联网适配与跨环境确定性验证；不把它们混入收尾导致重构无限延期。

## 10. 切换与回退策略

每个迁移单元先在新内核隔离场景验证，再以状态所有权为单位接入主游戏。禁止同一实体的位置、生命或订单由两套系统推进。

接入时登记：被替换写入口、命令转换、单向只读镜像、消费方、失败回退方式和桥接退出阶段。只有闭环完整且验证通过才移除旧实现；若其他功能仍依赖旧写入，继续隔离或先迁移依赖，不靠双向同步暂时掩盖。

需要回退时回退整个功能切换提交及其配套桥接；不支持把新内核存档读回旧实现。旧代码保存在版本历史即可，不建立永久双引擎运行模式。

## 11. 工作包与进度记录

Rxx.x 是可派发工作包；一个工作包可由多个小提交组成，不承诺一包恰好一个 PR。每个工作包要求：

- 写明入口条件、涉及文件/状态及不涉及的范围。
- 完成内核行为、适配、失败路径、测试与必要快照字段。
- 给出可重复验证入口、版本与实际结果，不只报告“编译通过”。
- 同时更新旧测试 → 新测试映射与过渡桥接退出记录。

工作包状态使用：未开始、进行中、待验收、完成、受阻。里程碑只有通过退出门才完成；代码已写或测试未跑均不是完成。

证据建议位于 `docs/verification/rts_kernel/Mx/`，包括行为差异、测试输出摘要、内容/地图版本、性能采样和未解决问题。不提前创建空报告或填造数据。

本计划按单条开发主线排序，不依赖多人并行。如果之后增加人员，可在契约冻结后分别做表现接入、用例迁移或测试夹具；共享状态写入口不能由多条未协调分支同时切换。

## 12. 节奏、风险门与近期启动清单

当前缺少真实生产率、工具链验证与性能样本，因此不编造周数和截止日期。M0 后评估 M1–M3 工作量，G3 后再评估 M4–M7；按实际完成速度和阻断项滚动调整，设计范围不随估时漂移。

最应提前暴露的风险及所在门：

- .NET 接入、导出与包同步：G0/G1。
- 寻路质量、浮点/固定帧行为及拥挤性能：G2/G3。
- 状态单源与恢复完整性：从 G1 起每门检查，不能到 M6 才发现。
- 效果表达能力与取消/叠加语义：R05.1–R05.4 用真实技能验证。
- 大规模联动与桥接成本：G3 先冻结预算，G7 做全量压力验证。

开发开始时按顺序执行：

1. R00.1–R00.3：固定地图、行为与状态写入者清单。
2. R00.4–R00.5：记录现状性能，确认 .NET 工具链和工程布局。
3. G0 通过后做 R01.1–R01.4，尽快显示第一个由纯 C# 控制的实体。
4. R01.5 与 G1 通过后进入真实导航，不能以演示实体替代完整移动实现。

架构风险导致改设计时先更新对应契约与测试预期；规则优化记录有编号 TODO，在独立阶段处理。本次路线图交付只修改文档，不创建工程、不运行或删除游戏实现。
