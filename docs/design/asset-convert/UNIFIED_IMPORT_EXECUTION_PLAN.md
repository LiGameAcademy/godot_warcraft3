# 魔兽资源统一导入管线执行策划案

日期：2026-09-27。状态：阶段 A 首版与独立资产查看器已实现，后续保真修复尚未完成。实际扫描结果和下一批顺序见 [首轮审计结论](AUDIT_BASELINE_2026_09_27.md)。

## 目标与已确认决策

建立“来源可追溯、数据不静默丢失、自动分类、统一生成、可重复验收”的资源管线。保真基座默认启用，增强效果独立可选；先解决保真缺口，再制作增强效果。

- 全量扫描当前解包资产；包括单位、建筑、装饰物、投射物、技能、光晕等所有模型，记录关联纹理和配置依赖。全量扫描不等于立即全量转换或逐个目视验收。
- 同时使用原作模型查看器和游戏内表现作为参考，冲突时以经典游戏内表现为准。Godot 查看工具用于诊断，最终还要在游戏场景验收。
- 光晕按用途重构：地面英雄光晕、武器／挂点光晕、悬浮光团、地面法阵等分别处理，保留原始纹理、颜色、时序和空间关系。
- 使用 Godot 原生节点、粒子或 shader 可以属于保真实现；是否“增强”取决于是否改变原作表现，而非采用哪种技术。
- 目标为 PC、当前项目的 Forward+ 渲染器；以百个同屏单位的常规战斗作为首轮性能测试场景。硬性性能预算在实测后确定。
- 尽量完全自动化。只有通用规则无法可靠处理时才考虑人工配置，逐项说明原因；不把逐模型调参作为默认工作流。
- 游戏与地图编辑器共享资源和实现。`.scn` 可以依赖统一管理的纹理、材质、脚本；运行时无需解析原始魔兽模型。
- 暂不建设面向其他 Godot 项目的独立资源包。用户追加确认建设独立 Godot 资产查看器：`apps/asset_viewer`，共享现有资源和代码，首版与阶段 A 一同交付。
- 首阶段交付全量审计报告、问题分级、代表样本集、按优先级排列的修复任务；后续分批修复并验收。

## 当前工作流判断与已知证据

“解包 → 转换 → bake 为 `.scn` → 游戏／编辑器加载”的方向合理，应继续沿用。`.scn` 是运行资源的交付格式，不能自动补回转换时丢失的信息，也不会保存某一帧粒子模拟画面。应保留数据语义、正确映射行为，并验证保存后重新加载的结果。

以下是代码检查发现的风险点，不代表全库受影响数量已经确定：

1. **转换时信息简化。** [转换器](../../../tools/asset-convert/src/convert-mdx.js) 中 PE2 的 Speed、Gravity 等参数按数字输出，动画对象可能转为零；材质主要通过 `pickDiffuseLayer` 选取一层，不能等同于完整多层材质还原。
2. **信息保留但消费不完整。** 同一转换器写出 `geoset_anims` 和 `texture_anims`；本轮在 `packages/` 和 `tools/godot/` 未找到同名消费入口。审计需继续追踪是否存在其他转换路径。不能把这类问题笼统称为“数据被丢弃”。
3. **保真与增强混合。** [MapModelCache](../../../packages/map/infra/map_model_cache.gd) 的 bake 流程自动调用 FireballMissileModern／Wc3FxPresenter；[FX Presenter](../../../packages/map/presentation/wc3_model/wc3_fx_presenter.gd) 根据几何和材质特征替换部分外观。这些改造应进入显式增强配置，或在有原作证据后成为保真映射。
4. **光晕依赖启发式。** 当前根据法线阈值区分脚底和其他部分；[光晕 shader](../../../assets/shaders/wc3_team_glow.gdshader) 使用统一提亮且禁用深度测试。需要按源标志、用途和游戏参考逐类确认遮挡、朝向、强度，不能统一换成一个软圆。
5. **已有成果可复用。** 粒子、Ribbon、重载测试和内容签名已有基础，见 [特效烘焙与验收](FX_BAKE_FIDELITY.md)。该文档中的历史测试结果不作为本次全量验收结果；其中遗留限制纳入新的问题清单。

根因按“源数据不足／导出丢失／中间数据未消费／映射近似／主动外观改造／加载或集成错误”分别归档，避免只调整亮度掩盖真正问题。

## 管线与职责

目标流程：来源清单 → 只读特征审计 → 版本化中间数据 → 能力检查与自动分类 → 保真编译 → 可选增强 → `.scn` 与依赖清单 → 重载、实机及性能验收。

### 来源与中间数据

- 以规范化的模型逻辑路径作为资源身份，保留原始路径大小写；记录来源包、覆盖优先级、源内容哈希、解析器和转换器版本。
- 扫描范围以实际可访问源文件清单为分母。重复路径、补丁覆盖、未解包资产、缺少依赖分别统计；不能将当前转换子集描述为完整经典客户端资产库。
- 原始数据缺失时可审计已有转换产物，但标记 `source_unavailable`，不能声称完成源数据无损检查。必要的重新解包任务单独列出。
- 保留全部已解析的相关字段、原始标志、关键帧、插值方式、全局序列引用、节点关系、材质层与纹理引用。对尚未识别的块保留源定位和诊断，不承诺现有解析器已经无损。
- 审计从源解析结果直接提取特征，不能只依赖已经被简化的 glTF 或旧 sidecar。
- 尽量扩展现有 sidecar，加 schema 版本和迁移规则；是否合并为单一中间格式由审计结果决定，不先重写整条转换链。
- 原始文件只用于离线转换和追溯；生成资源不依赖临时 staging 路径。参考 [资产分道约定](../../architecture/ASSET_LANES.md)。

### 自动化与分类规则

分类依据依次采用源语义和标志、材质及节点关系、对象数据中的用途关联，最后才采用名称或几何启发式。单个模型可以同时包含多个特效类别，不强制整个模型只选一种实现。

自动扫描、分类、转换和技术回归可以自动化；原作视觉一致性仍需有可核验的参考。低置信度对象进入待复核清单，记录触发规则、证据与候选实现；不自动认定为保真通过。

规则配置按“通用语义 → 类别规则 → 少数模型例外”生效。例外需要记录适用路径、源版本、原因、证据及回归样本，保存于生成目录之外；每个例外都应评估能否提炼为类别规则。

每个模型的审计记录至少包括：

- 身份、来源哈希、依赖、源和生成物是否存在。
- 网格／骨骼／动画／材质层／纹理动画／Geoset 动画／PE1／PE2／Ribbon／光源／billboard／事件／挂点等源特征及数量。
- 每种特征的导出状态、Godot 消费状态、已知近似和缺失字段。
- 自动分类结果、规则 ID、置信等级和理由。
- 严重性、影响范围、建议修复模块、代表样本关联。
- 技术检查状态、查看器检查状态、游戏参考检查状态及证据位置。

“支持程度”“实现方式”“验收状态”独立记录。例如原生 GPU 粒子可以是保真实现，但仍处于未完成游戏参考验收的状态。

### 分级与处理顺序

- P0：解析或加载失败、主要几何／依赖缺失、崩溃、生成物损坏。
- P1：影响识别或战斗阅读的明显错误，如投射物主体缺失、挂点错位、生命周期错误、光晕错误遮挡、主要材质动画未实现。
- P2：可运行但有明显近似，如尾迹形状、透明排序、渐变、次要材质层偏差。
- P3：可选风格增强和低优先级观感微调。

严重性与验证状态分离，未知不等于 P3。排期综合问题严重性、涉及模型数量、游戏使用频率与修复成本，优先修复一项即可改善多个模型的共性问题。

### 保真基座与增强

- 默认编译保真 profile；模型身份加 profile 共同决定产物和缓存身份，避免两种结果互相覆盖。
- 原始中间数据不受增强修改。增强通过独立配置调用可选处理阶段，默认关闭。
- 审计现有 visuals、Presenter、Fireball 专项处理和运行时 fallback 的优先级。查看工具显示实际加载路径、profile 和签名，避免拿旧覆盖资源验收新 bake。
- 重复挂载、重复增强及运行时再次修饰已烘焙节点必须可检测；一份资源在游戏与编辑器中执行相同规则。
- `.scn` 保存后重新加载检查节点、材质、动画、脚本和外部引用。签名覆盖源、schema、规则、profile、依赖、转换与运行代码、shader 和 Godot 版本；失败不更新成功清单。
- 不支持的特征产生可检索诊断。阻断级错误不得标记 bake 成功；允许的近似需在清单显式声明。

## 分阶段任务与完成条件

### 阶段 A：全量审计和实施排序（下一步首先执行）

工作包 A1：冻结扫描清单，确认源版本、覆盖关系、解析器能力和缺失文件。记录扫描范围与排除理由。

工作包 A2：实现只读审计入口，支持批量、断点恢复、确定性排序；单模型失败不终止其余扫描，最终汇总失败并返回明确状态。每个源模型必须有一条成功或失败记录。

工作包 A3：建立“源特征 → 导出字段 → Godot 消费 → bake → 运行加载”的能力对照，定位数据损失发生的阶段；关联当前工程的增强与覆盖路径。

工作包 A4：自动选取代表样本。必含牧师攻击投射物、大法师攻击投射物及英雄光晕；通过单位武器数据验证真实模型引用，不只凭文件名猜测。补充各光晕类别、多层材质、纹理动画、粒子动画、Ribbon、全局序列和失败模型。初始目标约 12–20 个，按特征覆盖去重，必要时扩展。

工作包 A5：输出机器可读报告和人工阅读摘要，形成带影响数量、源证据、修复位置、验证办法及依赖关系的任务清单。审计产物建议放本地 `.cache/asset-audit/<run-id>/`，schema、工具与经过整理的结论进入版本管理。

完成条件：扫描清单内所有模型均有记录；总数与分类、失败、跳过项可核对；缺少源和缺少原作参考单列；每个 P0／P1 共性问题均有可复现样本或明确说明无法复现的原因；修复任务可以独立领取执行。

本阶段不批量改写既有 `.scn`，不以完成全库保真修复作为审计交付条件。

### 阶段 B：统一契约与保真／增强分离

基于 A 的结果完善中间数据 schema、能力诊断和 profile；拆分当前混合的外观处理；明确两应用的资源加载与 fallback 契约；扩展缓存签名和加载诊断。保留旧产物可恢复的迁移路线，新流程先在样本集试用，再推广。

完成条件：默认保真路径没有未声明的增强；两种 profile 可区分并独立重烘焙；同一样本在两应用加载同一版本；改变规则会触发重建，未改变输入不会无故重建；保存重载不丢关键配置。

### 阶段 C：共性保真修复与光晕重构

由 A 的实测结果调整顺序，预期优先处理材质层及动画数据、PE2 动画参数和时钟、投射物主体与尾迹、各类光晕、Ribbon 剩余缺口。

光晕分类实现需分别定义载体、挂点、朝向、尺寸、纹理、队伍颜色、渐变、生命周期、深度测试和雾行为。画面深度遮挡与战争迷雾是不同责任，不混为一个开关。模糊案例保留证据和原始数据，避免按法线或名称强制替换。

完成条件：每批修复对应一类能力与一组样本；有转换检查、磁盘重载检查、真实渲染结果与游戏参考结论；未解决近似明确列出，不以增强模式的视觉改善代替保真验收。

### 阶段 D：批量生成、双应用验收与性能基线

按审计清单分批 bake；验证依赖闭包、缓存命中、失败重试和完整汇总。覆盖默认 profile，并检查增强 profile 不污染基座。

以百个同屏单位场景测量无特效基线与战斗特效增量；记录机器、GPU、分辨率、驱动、引擎版本、相机、可见单位／特效／粒子数量、CPU／GPU 帧耗时、帧时间分位数、内存和峰值。预热后固定时长采样，重复运行检查波动。

特效并发量由实际战斗记录形成基线，另测更高负载；不把“百个单位”当作固定特效数量，也不预先声称达到某个帧率。根据测量结果再制定容量、降级或池化预算；降级策略独立于保真参考设置。

完成条件：迁移范围内每个模型有明确处理结果；双应用抽样加载通过；代表样本完成视觉验收或列明外部参考阻塞；性能报告可复现，后续优化有量化依据。

### 追加工作包：独立资产查看器

采用 `apps/asset_viewer` 独立项目，复用共享包与真实渲染测试方式。首版提供模型搜索筛选、动画选择／暂停／重播、队伍色、相机、背景、地面和审计信息。挂点显示后续补充，profile 切换等待阶段 B 契约建立；现有产物明确标记为未分离，不用界面开关冒充已经实现。

粒子时间检查优先采用重置后固定步长推进，不默认假设任意拖动时间轴能还原历史模拟。显示的审计信息直接读取统一报告，运行资源直接加载相同 `.scn`，不另建转换实现。

查看器保持只读，不触发隐式转换或 bake；不为查看器引入跨项目资源打包。使用说明见 [资产查看器](../../../apps/asset_viewer/README.md)。

## 验收方法与证据

技术检查包括源字段保留、插值与全局序列、挂点和坐标、材质标志、依赖解析、磁盘重载、缓存失效与重建。每次修复选择能覆盖问题的测试，不为字段赋值本身堆积测试。

视觉检查固定模型、动作、时点、队伍色、相机和环境，记录参考来源与版本。覆盖出生、循环、攻击、死亡及结束后清理；投射物增加运动、转向与尾迹；光晕增加地面倾斜、遮挡、挂点、队伍色与远近观察。对随机粒子比较形态、密度、运动和时序，不要求跨引擎逐像素相同。

自动截图与 headless 测试只能证明各自检查范围，不能替代原作游戏内验收。没有可用原作参考时继续技术检查和缺陷修复，相关视觉条目标记“待参考”，不伪造通过结论，也不要求用户先提供样本才能开始全量审计。

原作查看器与游戏内冲突的条目保存两份证据，并记录采用游戏内表现的原因。正式阶段报告分别给出技术通过率、视觉已验收覆盖率及未验证数量，不合并为一个容易误导的“成功率”。

## 实施位置与首个执行批次

沿用当前目录职责：源解析和导出位于 `tools/asset-convert/`，bake 位于 `tools/godot/`，共享资产路径位于 `packages/content/`，模型和特效实现位于 `packages/map/`。游戏与编辑器消费共享包，不手改 `apps/*/packages/*` 生成副本。审计入口的准确文件名在 A1 后确定。

首个执行批次开展 A1–A5 和追加的查看器：确认输入清单 → 实现特征与能力审计 → 扫描全量 → 核对牧师／大法师引用与光晕样本 → 输出分级报告和阶段 B/C 的具体任务，并提供读取同一报告和现有 `.scn` 的查看入口。当前无需进一步询问产品偏好；完整客户端版本、原作参考和性能预算仍按执行证据逐步补齐。

计划不包含新的玩法开发、完整独立查看器、跨项目资源包、全库人工美术调参或优先制作增强特效。阶段 A 完成后，以审计证据细化修复批次，不把本策划案中的已知风险误写为已经完成的全库结论。
