# 资源缓存校验性能与取消（2026-10-07）

## 本轮范围

减少已有资源缓存启动时的校验等待，并使等待过程有进度、可以取消。仍对全部内容文件和场景计算 SHA-256；不以修改时间、文件大小或抽样代替内容完整性检查。源安装目录只读，资源查看器保持只读定位。

之前已有后台 `Thread` 和模型的线程加载。这次在缓存校验内部使用 Godot `WorkerThreadPool`，默认最多两个任务并行读取文件，可在引导场景的 `cache_validation_workers` 配置为 1～4。工作线程只处理文件和数据；路径挂载、界面更新和进入游戏在主线程完成。

每个文件使用独立 `FileAccess` 和 `HashingContext`，分块读取 1 MiB，不把整个 SCN 放进内存。取消在文件之间和块之间检查；线程组必须全部加入后才能处理校验结果。共享进度和停止状态由互斥锁保护。取消后不会挂载本次结果；覆盖“后台已完成、界面尚未处理”的取消时机。

引导每 100 毫秒读取进度快照，显示当前阶段、已校验/总文件数、本阶段读取 MiB、整次校验耗时。按钮在校验期间显示“取消校验”。关闭引导先设置取消，再安全加入线程；已经进入的系统文件读取调用仍需返回，无法保证任何磁盘状态下立即退出。

本轮不改变编译器、资产导入语义或场景缓存版本，现有匹配索引可以复用。

## 测量方法与结果

使用本机 Godot 4.7.2 .NET，对 `development-9beFl2/cache` 已发布索引进行只读测试：10,903 个内容文件（1,378,774,194 字节），480 个 SCN（728,962,261 字节）。每轮内容和场景哈希均通过；测试不挂载索引、不重新导入资产。

运行顺序为旧版原生串行、1、2、4、4、2、1、旧版原生串行。旧版基线使用 `FileAccess.get_sha256`；新实现包含清单预检、进度计数、分块检查与流式哈希。原始结果在 `tmp/cache-hash-benchmark.json`，运行日志在 `tmp/cache-hash-benchmark.engine.log`。

| 方式 | 第一轮内容/场景/合计（秒） | 第二轮内容/场景/合计（秒） |
| --- | --- | --- |
| 旧版原生串行 | 147.15 / 48.04 / 195.19 | 10.26 / 4.14 / 14.40 |
| 新版 1 个任务 | 8.11 / 3.68 / 11.78 | 12.22 / 4.08 / 16.30 |
| 新版 2 个任务 | 4.90 / 1.96 / 6.86 | 7.01 / 2.35 / 9.36 |
| 新版 4 个任务 | 5.15 / 1.94 / 7.09 | 6.02 / 2.41 / 8.42 |

系统文件缓存没有清空，机器上的其他程序也未隔离，不能把首轮 195 秒与后续 7 秒直接当作同条件加速倍数。本轮支持双线程有实用收益的判断；四线程没有稳定胜出，默认选两个任务，减少磁盘与 CPU 争用。这里统计的是哈希校验，不是整个游戏启动时间。

复测时，在仓库根目录 PowerShell 执行：

```powershell
$godotBinary = 'D:/GameMaker/Godot_v4.7.2-stable_mono_win64/Godot_v4.7.2-stable_mono_win64_console.exe'
$cacheIndex = (Get-ChildItem -LiteralPath 'tools/asset-convert/tmp/development-9beFl2/cache/indexes' -Filter '*.json' | Sort-Object Name -Descending | Select-Object -First 1).FullName
Copy-Item -LiteralPath 'tests/integration/asset_cache_hash_benchmark.gd' -Destination 'apps/game/tmp/asset_cache_hash_benchmark.gd'
& $godotBinary --headless --path apps/game -s res://tmp/asset_cache_hash_benchmark.gd -- --index $cacheIndex --report "$PWD/tmp/cache-hash-benchmark.json"
```

先确认该索引仍引用完整文件。路径不存在时使用当前成功导入批次中的索引，不要将文件名占位符原样输入 PowerShell。基准按普通索引内容检查文件，不判断当前游戏构建是否应接受这个索引；真正恢复兼容性由游戏回归验证。

## 自动与手动验证

新增常规回归：

- `selftest_asset_cache_validation.gd`：1/2/4 个任务完整读取、字节计数、两阶段校验、损坏/缺失/重复/越界路径拒绝、大文件中途取消、文件未被修改。
- `selftest_asset_cache_wizard.gd`：实际场景进度、取消按钮恢复、取消后不挂载、完成后取消竞态、关闭时安全加入线程。关闭回归使用 64 MiB 夹具；取消响应依赖正在执行的文件读取，不能承诺固定磁盘延迟。
- 既有缓存锁、一次性恢复测试与正式 Windows 发布引导流程继续执行。

手动使用本轮重新导出的游戏，保留成功导入缓存并启动。校验期间应看到文件数、MiB 和秒数变化；点击“取消校验”后停在资源准备页，“开始导入/重试”恢复可用，“继续进入游戏”不可用。取消不会损坏原索引，退出重启应重新完整校验并正常进入。正常进入后确认水元素出生和大法师施法结束、连续暴风雪、群体传送仍正常。

## 发布包实际回归与限制

Windows 发布引导 12 项回归通过：`tools/asset-convert/tmp/wizard-Q3OaEv/report.json`。完整游戏重新导出、复用已有 480 场景缓存的离线地图和技能回归也通过：`tools/asset-convert/tmp/development-9beFl2/report.json`，`reusedColdImport=true`，没有新做一次全量冷导入。

发布包第一遍后台校验实际为内容 292.56 秒、场景 50.76 秒，路径安装 2.657 毫秒；进程总计 373.7 秒。随后的 OpenGL 和 Vulkan 渲染进程分别约 28.1 秒、79.2 秒。这与编辑器基准差异明显，因此**首次读取慢仍未解决**。并发校验、进度与取消有效，不代表玩家第一次启动一定只需 7～9 秒。后续应记录导出程序逐文件打开、读取和哈希耗时，区分文件缓存、系统 I/O 和程序启动开销，不能未经测量归因于杀毒软件。

新增取消夹具曾在并行导出时超时；缩减到 64 MiB 并在无关首帧完成后直接观测校验进度，消除“文件已读完才开始观测”的测试竞态。修正后通过，关闭加入约 11 毫秒。导出/退出仍存在既有编辑器及资源清理告警，未将其算作修复。

## 下一轮：运行长帧

启动哈希优化不能证明技能释放期间的长帧已解决。下一轮先测量实际 Vulkan 游戏中首次/重复释放技能与首次肖像加载，将磁盘/资源解码、实例化、渲染资源首次上传、脚本更新和导航计算分别计时，再选择优化点。

优先处理确实同步加载的入口与重复重建，按需预热常用技能资源、分帧处理主线程工作。只有纯数据计算或受支持的资源加载进入后台；场景节点、材质实例修改和 GPU 交互仍遵守引擎线程边界。不为了“多线程”同时改写导航、技能规则或增加通用对象池。

冷导入末尾的内容复核调用仍同步等待线程组，场景复核仍串行；启动后地图节点实例化与显卡资源创建也没有因本轮变成后台任务。默认 D3D12 阻塞、真实干净 Windows 安装和原作视觉裁定继续分别验收。
