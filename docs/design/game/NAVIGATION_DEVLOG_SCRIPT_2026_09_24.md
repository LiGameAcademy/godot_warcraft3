# 视频文字稿 v1｜为什么点一下地面，游戏会卡住？

形式：开发日志，第一人称口播，不展示代码。按自然语速预计约 8–10 分钟，最终以试读为准。

主线：一次地面点击 → 导航的分工 → 重复工作如何拖慢响应 → 同条件实录 → 下一步取舍。

本稿中的方括号是剪辑提示，不朗读。数字只使用本次已核验记录。插图均为概念示意，不充当真实游戏画面或性能证据。

## 01｜开场：一个最基本的动作

[先播放旧版单独实录。从倒计时切入，完整保留约 2.7 秒的停顿；停顿期间留白，不用音乐音效刻意夸张。随后切当前版。]

我最近在做一个 RTS 项目。

前段时间，我碰到了一个特别影响手感的问题：给单位下达移动命令，游戏有时会明显卡一下。

从玩家的角度看，这件事应该非常简单。我点一个地方，你走过去。走不过去，也应该尽快告诉我。

但看这段画面。旧版正在处理一条移动命令，连左边的监视面板和上方的时钟都一起停住了。

同样的单位，同样的目标，换成优化后的版本，命令很快就返回了。

这一期，我想聊聊这次重构背后的思路：一次移动到底包含哪些工作，之前为什么会慢，以及改快之后，为什么我还不认为导航系统已经做完了。

## 02｜点一下地面，背后有三件事

[游戏全景 → 英雄绕建筑实录 → 插图 01。字幕依次强调：找路线、整理路线、走过去。]

先把“寻路”这个词拆开。

第一件事，是找路线。

你点的位置，和单位现在站的位置之间，可能隔着建筑、树林，或者单位根本通不过的区域。系统要先判断：有没有一条符合通行规则的路？如果有，大致怎么绕？

第二件事，是整理路线。

搜索得到的路线，可能像沿着格子走楼梯，有很多小拐点。但如果中间一段可以直接通过，就没必要每一步都拐一下。

这里又有一个限制：单位有体积。一条线能擦着墙过去，不代表一个单位也能挤过去。整理路线的时候，仍然要检查障碍和通行空间。

第三件事，才是让单位真的走过去。

到这一步，问题又变了：前面有别的单位怎么办？几个人都想站在同一个位置怎么办？路线中途被挡住怎么办？

所以我们看到的是一个移动动作，系统里却同时有路线规划、路线整理和移动执行几个层次。

这次优化，我先集中处理的是前面这些工作为什么会拖住游戏。

## 03｜旧版慢在哪里

[插图 02；局部缓慢推近左侧“重复计算格点结果”。各行是共享部分区域的候选线段，不与真实耗时刻度绑定。]

旧版最大的感受是：命令一发出去，整幅画面有时就不动了。

顺着这个现象往下看，会发现移动命令里的寻路工作是同步执行的。也就是说，这一轮计算没结束，主线程就没法及时回去更新画面。

单位一多，几次查询还会连续加在一起。

但“同步执行”只是卡顿呈现出来的方式。还要继续问：这些计算为什么会花这么久？

我在这次检查里发现了几类重复劳动。

首先，旧版有不少搜索和通行检查放在脚本里做。当搜索范围变大，这些细小操作累积起来就很贵。

其次，路线整理会反复检查已经检查过的路段。

可以把它想成：我要判断能不能从起点直接走到前面的某个位置。先检查一小段，再把刚才那一段重新检查一遍，然后继续向前。路线越长，前面那段路就越容易被来回检查。

还有一种情况：第一次搜索失败了，准备换个起点再试。但如果调整之后，起点其实没有变化，就等于把同一个失败问题又算了一遍。

这些问题单独看都不一定显眼，叠在一次移动命令里，就会变成玩家能感觉到的停顿。

## 04｜这次怎么改

[使用新增的“三项优化配图”：讲第一点时切 01_交给引擎原生搜索；第二点切 02_减少路线重复检查；第三点切 03_避免无意义重试。随后接路径线实录。三张均为 1920×1080，存放于 tmp/navigation-devlog-episode/三项优化配图。]

这次的改法，可以概括成三件事。

第一，把默认的网格搜索交给引擎提供的原生实现。

我们仍然负责定义哪里能走、哪里被挡住、单位需要多少通行空间，以及什么情况下不能斜着穿过墙角。只是大量重复的底层搜索工作，换成了更适合承担它的实现。

同时，把常用的准备工作提前做掉，尽量别等玩家发命令的时候，才临时把一整套数据建起来。

第二，减少路线整理中的重复检查。

检查能直接走多远时，先逐步扩大探测距离，再在需要的地方细化。一次查询里已经算过的通行结果，也尽量复用。

这里没有放宽“不能穿墙”的要求。最后接受的路线，仍然要通过完整的通行检查。

第三，避免没有意义的重试。

如果失败之后，新的尝试条件根本没变，就不要原样再算一遍。

所以这次并不是只换了一个算法名字。搜索、路线整理、准备时机，以及失败处理，几处工作一起减少了这条命令的成本。

还有一个挺有意思的插曲：我试过另一种搜索选项。它在简单测试地图上表现更好，但到了真实地图的某些失败查询里，反而更慢，最后没有启用。

这也提醒我：优化最终要看项目里会遇到的问题，不能只挑一个好看的测试结果。

## 05｜用同一条命令看结果

[播放 13 秒左右对照，左 BEFORE，右 AFTER。先看停顿，再切各自全幅截图，放大最后两项读数。持续小字：单单位／同一不可达目标／原速固定命令回放。]

回到开头这段对照。

为了让条件尽量一致，我从 Git 里单独取出了旧版本，用相同的地图、单位、目标坐标和监视面板，分别回放同一条命令。

这里要特别说明：这是一个走不到的目标，两版最后都返回失败。它展示的是失败搜索带来的卡顿，不代表每一次普通移动都要花这么久。

这次录制里，旧版的命令返回耗时大约是两千六百八十一毫秒，也就是两秒六八。当前版大约是十三点七七毫秒。

这两个数字测的是命令调用本身，不是从鼠标点击到画面出现反馈的完整时间。

左边这个 Panku 面板也值得看一下。单看即时帧率，其实容易错过问题：卡住的时候，监视面板自己也没法刷新；恢复之后，那个尖峰又可能很快过去。

所以我另外保留了本次命令耗时，以及这一小段回放里的最大帧间隔。

当前版的最大帧间隔仍然接近四十七毫秒。这说明这类长停顿有了明显改善，但还不能说游戏已经稳定六十帧，更不能把这一次结果推广到所有地图和单位规模。

## 06｜算得快之后，还缺什么

[七单位移动实录 → 插图 03。字幕：下一步，不是已完成功能。]

那现在的导航系统算完备了吗？我觉得还没有。

接下来更值得关注的，是一群单位走在一起时，会发生什么。

有路，但通道太窄，大家要怎么过去？前面的单位停住了，后面的单位是等待、绕开，还是重新规划？玩家刚下达一个新命令，上一个还没算完，又应该听哪一个？

这些问题，不能只靠把一次搜索再加速一点来解决。

如果以后把寻路分批处理，就还要考虑取消和替换。否则辛辛苦苦算出一条路线，单位却早就收到新的命令了。玩家按下停止之后，旧结果也不能又把它推着走。

所以我想对标的，是玩家对成熟 RTS 的那些基本期待：命令响应清楚，单位行为可以理解，受阻之后不会莫名其妙地当作已经到达。

至于更复杂的编队、更大的单位规模、更精细的互相避让，都需要结合我们真正要做的玩法，再决定投入多少。

## 07｜什么时候继续做 MVP

[回到干净的游戏全景；依次出现三行字幕：失败反馈、拥堵与重规划、真实玩法验收。]

这也回到了我最近一直在想的问题：是继续横向把 MVP 补起来，还是停下来，把一个系统不断往深处打磨？

我的取舍是：先修那些会打断基本体验的问题。

点一下地面，整幅画面停住几秒，这种问题会影响后面所有玩法，值得先停下来处理。

但当这个主要障碍缓解之后，我不想马上把导航扩展成一个无限重构的项目。

我会先把失败反馈、受阻后的处理，以及代表性的群体移动场景验证清楚。确认这些底线，再回到完整的游戏流程里，让采集、建造、战斗去暴露下一批真正重要的问题。

如果真实玩法证明，批量寻路已经持续拖累响应，再把调度和命令取消认真做起来。

对我来说，这期开发日志值得现在就记录。因为它既有一个已经看得见的改善，也保留了还没有解决的问题，以及当下为什么这样选择。

下一次再回看，我们就能知道：今天的判断，哪些经受住了实际玩法的检验。
