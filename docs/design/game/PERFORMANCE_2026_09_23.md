# 第二轮对战性能优化（2026-09-23）

## 范围与结论

保持玩法、画质、索敌频率和调试开关。先修复重复工作，再通过分项计时定位实际对战热点。无渲染批量查询的耗时不等于游戏每帧耗时，也不换算成游戏 FPS。

开局测量发现：邻居查询虽然批量测试较贵，实际调用次数较少；自动索敌才是主要 CPU 开销。优化前的一段 10 秒实时窗口中，自动索敌累计约 8.4 秒。单独优化命令卡、预约格和路径绘制，不能解决这个瓶颈。

## 实现

- **预约格**：`Vector2i → owner` 与 `owner → cells` 双向索引；只释放不再需要的格子，始终重试此前被其他单位占用的目标格。不抢占已有预约。导航停止、移除和更换预约表时释放所有权。
- **命令卡**：结构状态与冷却、法力可用状态分离。动态更新只重新计算当前可见的施法技能，并更新已有按钮；保留 0.1 秒冷却进度刷新，状态转换立即处理。按钮复用图标和冷却遮罩，图标加载失败仍允许重试。
- **路径绘制**：复用两个 ImmediateMesh 及材质；相同路径不重建，空路径只清空一次；移动中的起点仍实时更新。
- **模块装配**：命令卡、选中 HUD 使用依赖身份检查；依赖不变时不重建回调字典。首次创建、会话/节点替换和 shutdown 后重新绑定。
- **自动索敌**：先按原有敌对规则排除无关单位，再按精确攻击距离筛选，最后执行其余目标合法性检查。建筑占地半径只在单次查询内按类型复用；不跨帧缓存位置、目标或定义，保留建筑边缘距离及 `<=` 同距离选择顺序。
- **测量**：`MatchHotpathMetrics` 默认关闭，按热点保存总调用数、总时间及最近最多 2048 个耗时样本。窗口输出后清空。覆盖邻居、预约、寻路、索敌、命令卡、路径绘制、技能 tick、战斗 tick 与胜负检查。父子调用可能重叠，不能把所有项直接相加当作整帧时间。

邻居查询仍是线性扫描；这次不引入空间索引或延迟一帧的缓存。

## 微基准

Godot 4.7.2，固定 Echo Isles 开局、109 个单位宿主子节点；世界暂停后分别测量，每项预热 5 次、采样 120 次。以下为各跑三次后，平均耗时和 P95 各自的中位数（ms）。

| 项目 | 优化前平均 / P95 | 优化后平均 / P95 |
|---|---:|---:|
| 选中 HUD | 0.1104 / 0.156 | 0.1170 / 0.146 |
| 血条更新 | 1.4970 / 3.026 | 1.4937 / 2.745 |
| 血条同步 | 0.8094 / 1.628 | 0.8084 / 1.166 |
| 全部单位各查询一次邻居 | 7.3476 / 9.313 | 7.3887 / 9.271 |
| 300 个单位批量更新预约 | 21.3129 / 23.726 | 0.8917 / 1.454 |
| 空路径绘制 | 0.0154 / 0.016 | 0.0010 / 0.002 |
| 显式完整命令卡刷新 | 1.5377 / 2.507 | 1.5134 / 2.477 |

完整命令卡的单次耗时变化很小；收益主要来自冷却期间不再每帧完整刷新。以上表格测量发生在索敌额外优化之前，两组使用相同测量入口；索敌使用同场景保留的原算法作为独立对照。

### 自动索敌独立对照

在同一个暂停的 109 节点场景中，原算法和最终算法各执行三轮批量测试，并逐个断言目标选择一致：

| 算法 | 平均耗时中位数 | P95 中位数 |
|---|---:|---:|
| 原算法 | 225.584 ms | 252.159 ms |
| 最终算法 | 32.404 ms | 35.618 ms |

这是对每个宿主子节点分别查询一次的批量开销，下降约 86%。实际索敌次数由 AI 状态决定，不能直接把表中数值作为每帧成本。

两分钟固定 60 帧/模拟秒的对战测试：优化前平均帧耗时 29.97 ms，最终版本 14.10 ms；各 10 秒窗口 P95 的中位数为 182.04 → 36.78 ms，结束时均为 115 个宿主子节点。基线期间存在短暂回归进程并发，且后台应用未隔离，因此整帧数据只作辅助证据；上述同进程串行的原/新算法对照是更直接的证据。

邻居查询规模测试采用 100 / 300 / 600 个均匀分布的合成单位，每项预热 5 次、采样 20 次，批量平均耗时分别为 4.82 / 41.51 / 164.60 ms。这证实当前实现不适合大量单位每帧同时查询；后续空间索引仍有价值，但不能把该合成负载当作默认开局负载。

## 复现与观测

使用 `tests/integration/benchmark_match_hotpaths.tscn`，从项目根目录运行当前 Godot 可执行文件：

```text
--headless --path . res://tests/integration/benchmark_match_hotpaths.tscn
--headless --path . res://tests/integration/benchmark_match_hotpaths.tscn -- --acquire-compare
--headless --path . res://tests/integration/benchmark_match_hotpaths.tscn -- --scale
--headless --fixed-fps 60 --path . res://tests/integration/benchmark_match_hotpaths.tscn -- --soak --seconds=120
--headless --path . res://tests/integration/benchmark_match_hotpaths.tscn -- --soak --realtime --seconds=1800
--headless --fixed-fps 60 --path . res://tests/integration/benchmark_match_hotpaths.tscn -- --soak --fixed-units --seconds=120
```

普通 soak 使用固定 60 帧/模拟秒计数，应与 `--fixed-fps 60` 配对；`--realtime` 按墙钟时间退出，同时输出实际累计模拟时间。每个窗口标记是否结算，结算后的空闲帧不能当成持续战斗数据。固定单位模式关闭对手经济与军队的自动扩张开关，仍运行现有单位的行为。

渲染验证去掉 `--headless`，添加 `--resolution 1280x720`，并在用户参数中添加 `--camera-route`。保持项目 Forward Plus / D3D12 和默认画质。输出的渲染 CPU/GPU 数值是该窗口末帧的 viewport 测量值，不是整个窗口的 GPU P95；无渲染时为 null。

游戏内可在 Panku 执行 `perf.set_hotpaths_enabled(true)`，一段时间后执行 `perf.hotpaths()` 获取并清空一个窗口；结束后执行 `perf.set_hotpaths_enabled(false)`。不要常开统计来代表正式游戏的极限性能。

日志保存在忽略的 `tmp/round2-*.log`。后台应用没有强制关闭，短时差异应结合三轮中位数、操作次数和实际对战窗口理解。

- 现有命令卡（9）、路径调试（3）、缓存（77）、对战重开（21）、英雄生命周期（23）、无敌目标（8）检查通过。
- 群体移动、寻路组合、UnitAI 和战斗转向测试通过。
- 编辑器导入没有脚本解析或编译错误，`git diff --check` 通过。沙箱中的缓存测试最初因 `user://` 临时图片写入受限失败，获得该测试需要的目录访问后通过；导入时保存工作区外个人编辑器设置被拒绝，不影响项目脚本导入。

### 30 分钟会话与固定单位对照

- 会话连续运行 **1800.00 秒墙钟时间**，没有脚本错误或退出泄漏提示。
- 默认双方场景在 **约 10 分 51 秒**时首次记录到正常结算；因此后续是结算稳定性观测，**没有验证单局连续活动对战 30 分钟**。日志 `simulation_seconds` 是累计引擎帧 delta，结算后仍会增长，不能据此推算活动对战时长。
- 活动阶段从 110 个宿主子节点 / 4649 节点 / 463.45 MB，增长到结算时 126 个宿主子节点 / 5478 节点 / 491.29 MB。单位和资源同时增加，不能仅凭这个变化认定或排除泄漏。
- 结算后直到 30 分钟结束，节点 **5478**、对象 **24188** 保持不变，内存约 **491.30 MB**。剩余回归、导入和渲染测试在此结算阶段运行；这段空闲帧耗时不用于推断活动对战性能。
- 另跑固定规模 120 模拟秒：始终 **109** 个宿主子节点、**4573** 节点、**21187** 对象；内存 **459.912 → 459.920 MB**。平均帧耗时 **12.57 ms**，窗口 P95 中位数 **35.15 ms**。这段短窗口未见随时间明显累积的资源增长，不能代替更长时间的泄漏验证。

## 剩余瓶颈与下一步

**长期活动对战的卡顿尚未完全解决。** 在墙钟约 **361.5 秒**、122 个宿主子节点时，一个窗口出现整帧 P95 **1022.81 ms**。其中 **36 次寻路累计 7297 ms**，单次平均 **202.70 ms**、P95 **342.88 ms**；同期预约格更新、路径绘制与自动索敌保持较低开销。

下一轮应针对 `PathQuery.find_path` / `_astar` 及导航重规划触发源，记录起终点、搜索展开量和失败原因，确认是否存在同一不可达目标的重复请求，再优化重复搜索和搜索执行方式。本轮没有修改搜索上限、AI 更新频率、画质或寻路可达性规则，避免用行为退化掩盖峰值。
