# Gameplay 架构审查与双产品目标设计

日期：2026-09-23。状态：提案，尚未实施。基于四波次模块化重构后的源码检查。

后续讨论已细化为 [Gameplay 分层与目录重构实施策划](GAMEPLAY_REFACTOR_PLAN.md)：确定输入、命令、状态、行动四方面职责及表现边界。实际内部目录采用该文的职责命名；迁移批次以该文为准，本文保留总体架构与内容系统设计依据。

本文补充地图五层架构，不替换地图拓扑、坐标和资产车道契约。目标是独立发布游戏与地图编辑器，并使两者共享内容语义，为 Mod 提供版本化接口。目录树均为目标结构，不代表已经迁移。

## 1. 结论与范围

采用模块化单体：按功能划分边界，功能内部按需要分领域、应用、表现和基础设施。沿用 Godot 节点组件；暂不整体改成 ECS，不引入全局玩法事件总线，也不把每个功能改为 Autoload。

现在最值得做的是建立内容、状态和产品边界。继续缩短 GameDirector 只是结果，不能作为架构验收指标。本次检查覆盖启动配置、模块装配、实体/会话状态、技能扩展、资源解析与缓存和既有地图设计；不是对全部玩法算法的逐行正确性审计，也未重新运行性能基准。

已有优势：

- 地图 Data/Catalog/Logic/Presentation 分层已有契约，可作为共享库基础。
- Gameplay 已有功能模块、对局内生命周期、显式依赖绑定及重开回归；不用推倒重来。
- 单位已采用导航、采集、战斗等组件组合，模型替换与单位身份开始分离。
- AssetProvider、RuntimeAssets、MapModelCache、定义表工厂已经提供可迁移的资源基础设施；缓存已有预载和原型释放处理，并非从零建设。
- 请求用方法、结果用信号的现有约定适合继续使用。

## 2. 当前审查发现

优先级表示对目标架构的阻碍，不表示已确认线上故障。下列路径相对仓库根；函数名是定位依据。

| 优先级 | 证据 | 影响与改造方向 |

另外，`mods/` 当前检索到的文件只有 `.gitkeep`；内容包文档也将 manifest 注册列为后续事项。因此本提案是完善既有覆盖能力，不是已有完整 Mod 系统的重新命名。

## 3. 分层与依赖

```text
GameApp                         EditorApp
输入 / HUD / 对局入口            文档 / 工具 / 撤销 / 内容编辑
        ↓                           ↓
Gameplay 应用用例              共享地图与内容 API
        ↓                           ↑
Gameplay 领域规则 ───────→ 地图查询契约 / 内容定义契约
        ↑                           ↑
Godot 实现适配器              存储 / 解码 / 地图表现适配器
```

依赖箭头代表使用关系；基础设施实现内层声明的端口，由应用启动代码注入。地图共享库不导入 Gameplay；例如寻路算法如果双方需要，可放共享地图查询库，而单位移动、预约和订单属于 Gameplay。

功能内约定：

- `domain/`：规则、状态、小型值对象；允许 Vector2i、RefCounted 等基础类型，不依赖 SceneTree、HUD、文件路径或 Autoload。
- `application/`：训练、施法、建造、变形等用例；执行校验、状态提交和结果通知，通过窄接口使用世界、内容和资源。
- `presentation/`：输入、HUD、模型、特效、动画；发送命令并消费只读视图和结果。
- `infrastructure/`：Godot 节点访问、资源适配等具体实现。仅在有真实代码时创建目录。

不要求现有所有 `logic/` 文件立即改名；先修依赖，再搬目录。跨功能请求使用显式接口，完成事件用对局内信号；信号不能替代有成功/失败结果的事务调用。

### 工程原则落点

| 原则 | 可执行约束 |
|---|---|
| 单一职责 | 模型修复不负责包优先级；命令合法性不依赖当前选中/HUD；模块入口只协调本功能生命周期。 |
| 开闭原则 | 同类单位/技能通过定义新增；已有行为通过注册工厂扩展。真正全新机制仍允许修改系统，不追求完全零改动。 |
| 依赖倒置 | 用例依赖 WorldQuery、ContentView、SpawnPort 等窄契约；不依赖整个 MapLoader/Director。 |
| 接口隔离 | 选中 HUD 只获取视图，不能通过一个万能 context 得到伤害、生成和文件读写能力。 |
| 单一事实来源 | 每种状态只有一个写入所有者；缓存、HUD 和旧元数据只做派生或临时适配，不能双向独立写入。 |

## 4. 状态与组件设计

明确区分三类数据：

1. **ContentDefinition**：单位、技能、物品、科技、模型引用等定义。导入校验后冻结；修改需要生成新内容快照。Resource 本身可变，必须通过访问约定/副本或封装实现只读，不能仅靠命名保证。
2. **MatchState**：玩家库存、实体身份、位置、生命、订单、冷却等运行态。各系统有明确写入职责，GameSession 负责对局边界而非囊括所有逻辑。
3. **ViewState**：选中单位、肖像、命令卡、动画、特效。可由前两者重建。

建议保留 Unit 作为节点实体门面，逐步引入 EntityId 和 EntityRegistry。现有 creation number 可作为迁移输入，但必须验证生成、重开和地图导入时的唯一性；Godot instance_id 不能成为跨存档/外部 API 的身份。

组件按能力组合，例如 Health、Mana、Orders、Inventory、Production；并非每个字段一个 Node。纯数据用轻量对象，需要 Godot 生命周期/物理回调的部分才用 Node。领域死亡状态与尸体动画分离：单位已经死亡时不能因动画仍播放而继续接受命令。

第一步通过类型化状态访问器包装现有元数据，保持原存储单源；随后逐组件搬迁权威状态并移除旧写入口，避免双写同步。WorldMembership 的进矿/施工在场性契约必须继续沿用。

玩家输入、AI 和未来触发器统一走应用命令，例如 `TrainUnit`、`CastAbility`、`ChangeUnitForm`。命令含实体 ID、请求玩家、参数；返回明确错误码/结果。执行入口再次检查所有权、费用、科技和当前状态，UI 检查仅用于提示。资源不足或目标失效时不产生部分扣费、部分入队等副作用。

## 5. 生命周期与 Autoload

| 生命周期 | 适合持有的对象 |
|---|---|
| 应用进程 | 设置、日志、内容包发现、资源加载服务；可通过少量 Autoload 启动，但内部使用显式注入。 |
| 内容快照 | 已验证定义、解析索引、内容版本、关联资源缓存。 |
| 对局 | 世界状态、命令服务、战斗/导航/采集/生产系统、AI、对局事件订阅。 |
| 本地视图 | 输入、选择、HUD、相机、视觉调试。 |
| 编辑文档 | 地图修改、撤销栈、预览内容版本。 |

GameDirector 最终保留场景引用与入口转发；`MatchComposition` 构造依赖，`MatchRuntime` 管理启动/推进/停止，功能模块负责自身资源释放。无需为三个名字强行立即创建类：先把构造和业务用例分离，有独立责任再落类。

停止时拒绝新命令、作废异步请求、断开订阅、释放实体与对局资源，最后释放内容快照引用。保留现有绑定代次与重开测试。编辑器试玩首选独立游戏进程；将来嵌入试玩也应创建完整隔离的 MatchRuntime。

## 6. 两个产品与目录

建议同一仓库维护两个独立 Godot 项目，共享包只有一个源码来源：

```text
apps/
  game/                         # project.godot、启动场景、应用 UI、发布配置
  map_editor/                   # project.godot、编辑文档/工具/UI、发布配置
packages/
  content/                      # manifest、定义 schema、解析/加载契约及适配
  map/                          # 地图格式、查询、地形表现；不引用游戏应用
  gameplay/                     # 对局运行库，可供游戏及试玩使用
    match/
    entities/
    features/
      combat/{domain,application,presentation}/
      production/{domain,application,presentation}/
      ...
  foundation/                   # 确有跨包需求的小型日志/通用类型
content/
  builtin/                      # 自有内容定义、清单；大体积转换产物另行管理
  samples/                      # 最小地图、示例 Mod、教程内容
tools/
  content_pipeline/             # WC3 导入转换适配，不进入通用领域规则
  workspace/                    # 共享包同步、依赖锁定、导入与构建脚本
tests/{contracts,architecture,integration,performance}/
docs/{architecture,tutorials}/
```

Godot 的 `res://` 是项目根，不能把仓库父目录当成两个项目天然共享的资源根。建议构建/开发同步工具将所需 packages 复制到各项目的生成目录 `packages/<package>/`，统一资源路径；源文件只在 packages 编辑，生成副本禁止编辑，记录内容哈希并检查同步状态。不把 Windows 符号链接作为必需前提。

迁移须连同 `.gd.uid` 保留并检查场景、脚本、字符串路径、动态加载及 class_name。两个项目各自导入，不在单个项目里保留两份相同共享源码；明确包清单和依赖顺序。原项目保留到两个入口验收通过，随后再移除旧路径适配。

游戏发布不携带编辑器 UI/工具和离线转换工具；编辑器默认共享地图和内容库，试玩通过启动游戏制品传入地图包与内容锁定文件。需要嵌入试玩时再显式依赖 gameplay。编辑器导出内容若选择 Godot PCK 管线，需要单独解决工具版引擎的可用性，不能假设普通导出程序自带完整导入/导出工具链。

## 7. 运行时内容与 Mod API

### 统一加载链路

```text
发现包 → 校验 manifest/schema/依赖 → 确定加载顺序
      → 合并定义并校验引用 → 创建 ContentSnapshot
      → ContentId 解析为 AssetRef → 加载/解码 → 缓存 → 实例化
```

ContentId 使用命名空间，例如 `base:unit/footman`；WC3 FourCC 通过兼容映射保留。资源引用使用内容 ID，物理路径只在适配层出现。模型 Edition 选择与包覆盖优先级继续保持正交。

manifest 至少包含包 ID/版本、schema_version、所需 API 版本、依赖范围、定义/资源入口、显式覆盖声明。锁定文件记录准确版本、内容哈希和加载顺序。循环依赖、缺依赖及未经声明的重名覆盖应产生可定位错误；顺序不能依赖目录枚举结果。区分整表替换与按 ID/字段补丁，第一版优先支持整条定义替换，避免含糊的数组合并规则。

建议先确定以下小型契约，再写 SDK；表中名称为提案：

| 接口 | 输入/输出及职责 |
|---|---|
| ContentRegistry | 挂载前验证包，构造不可变快照，输出冲突/缺引用诊断和来源信息。 |
| DefinitionProvider | `get_definition(kind, id, snapshot)`；返回类型化只读定义或明确的缺失错误。 |
| AssetResolver | `resolve(asset_id, snapshot)` → AssetRef（来源包、版本、内容哈希、类型、存储位置）。 |
| AssetLoader | `request(ref, scope)` → 可查询状态/失败原因的句柄；支持取消、同请求合并与预算调度。 |
| WorldQuery | 根据 EntityId 返回只读状态；不暴露 SceneTree 或可写组件。 |
| WorldCommands | 提交版本化命令，复用正常游戏用例与合法性校验。 |
| BehaviorRegistry | 启动阶段注册受支持的 behavior_id 工厂；冻结后不得改变当前对局语义。 |

编辑器使用同一 schema、校验器和解析器生成内容，游戏加载相同快照；编辑器可另外拥有草稿模型，不能让未验证草稿直接替换游戏定义。

### 加载与缓存策略

- 文件系统、Godot 包资源分别实现存储适配器。保留现有松散 GLTF/图像解码器，不能直接把所有调用替换成 ResourceLoader。
- 缓存键包含内容快照/哈希、资源类型和导入选项；原型资源与单位实例分离。失败缓存同样绑定版本，不能让修复后的资源永久失败。
- 明确缓存生命周期、内存预算、在用引用和淘汰策略。对局退出释放其引用，实例仍在用的资源不能被强制销毁。
- 预载需求在开图阶段收集；运行中按预算完成解码/实例化。后台读盘、资源解码和主线程挂树分别测量，不能把“异步请求”当作无卡顿保证。
- 编辑器修改生成新快照并作废旧异步结果；游戏对局冻结快照。第一版切换 Mod 要重建对局，不支持中途卸载代码。

Godot 支持通过 `ProjectSettings.load_resource_pack` 挂载 PCK/ZIP，但覆盖已有路径和挂载时机需要明确控制；它提供容器能力，不提供本项目的定义合并和兼容性协议。包可能包含脚本，第一版数据 Mod 只接受受控数据/资产格式，不应直接实例化任意脚本场景并称其为数据沙箱。脚本 Mod 作为后续独立的可信扩展模式设计。[Godot 资源包文档](https://docs.godotengine.org/en/stable/tutorials/export/exporting_pcks.html)

对于适用 ResourceLoader 的资源，线程请求后应检查完成状态再取结果；过早 `load_threaded_get` 仍会阻塞。[Godot 后台加载文档](https://docs.godotengine.org/en/stable/tutorials/io/background_loading.html)

Mod 的路径入口应拒绝目录穿越/越过包根的引用，并报告具体包和字段；数据格式也需限制规模。这些属于开放外部内容后的输入契约。API 不暴露任意文件读写或内部 Node。脚本加载不能因上述 API 限制而被假定隔离。

## 8. 分波次实施与验收

每波保持可启动、可回归、可独立提交；目录搬迁与行为修改分开提交。

| 波次 | 工作 | 完成条件 |
|---|---|---|
| 0：契约基线 | 记录状态所有者、依赖图、两产品配置差异；补架构依赖检查 | 明确禁止引用及允许的适配边界；现有功能回归作为基线。 |
| 1：内容统一 | 引入快照/来源信息，让定义与资源经过一致解析；先兼容现有路径和 FourCC | 示例 Mod 同时修改单位定义和模型；编辑器与游戏解析一致；卸载后新对局恢复基础内容；缺依赖/覆盖冲突可诊断。 |
| 2：双应用边界 | 共享库清除应用目录依赖，建立复制同步工具和两个最小启动项目 | 干净机器/无开发缓存下导入、导出、启动；游戏无需编辑器目录；松散与随包资源都经制品测试。 |
| 3：状态与用例 | EntityId/状态访问器；优先迁移训练、建造、形态变更；分离输入/HUD | 玩家与 AI 同入口；失败无部分提交；死亡、移除、进矿、重开及所有权回归通过；迁移状态无双写。 |
| 4：行为与组件 | 技能行为注册、单位能力装配、表现订阅；迁移领域规则 | 用已有行为模板增加示例技能无需修改核心分支；无 HUD 环境可测规则；玩法结果保持一致。 |
| 5：加载服务与 SDK | 拆分缓存/解码/视觉修复、异步预算、诊断界面与 Mod 示例 | 取消/失败/切换版本无旧结果写入；缓存预算可观察；文档示例在两个制品验证；API/schema 版本规则稳定。 |

不必等第 5 波才测加载性能：第 1 波开始就记录解析、读盘、解码、实例化、缓存命中和内存，比较同内容同场景基线。现有寻路热点单独优化，目录和分层改动不能作为性能已经改善的证据。

教程按“内容定义 → 实体组件 → 应用命令 → 表现 → 编辑器生成 → Mod 加载”组织，每波保留可运行示例。无需提前发布一个覆盖所有内部类的 SDK。

## 9. 默认假设与后续决策

默认先支持数据/资产 Mod、启动时选择包、两个独立运行的应用，暂不承诺不可信脚本执行、战斗中热换包或多人确定性同步。若产品确定需要这些能力，需分别设计执行隔离、状态迁移或网络协议；不要把未来可能性提前变成所有模块的负担。

下一次实施建议从第 0–1 波开始：统一内容解析和定义来源，用一个最小 Mod 贯通编辑器到游戏，再以已经验证的包边界迁移目录。
