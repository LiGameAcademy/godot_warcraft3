## 结论

目录归位和请求/结果类型是合理的增量演进；定义表改走 overlay 修复了原有入口不一致的问题。但当前主要完成的是接口骨架，不能等同于状态权威、内容冻结、双产品发布和行为扩展的端到端验收。建议先修以下问题，再扩大 UI/Mod 对新接口的依赖。

## 可操作发现

### R1 [P1] 实体释放后的查询先强转，导致运行时脚本错误

位置：`game/entities/state/entity_registry.gd:35`，同类问题也在 unregister 的第 26 行。

`_by_id.get(...) as Node` 先于 is_instance_valid 执行；节点已经 free 时，强转就抛出 `Trying to cast a freed object`，后面的清理分支无法保护调用。最小复现为注册节点→free→get_node；本次已复现。count 仍为 1，反向索引也没有随实体销毁清理。后续通过 EntityId 查询死亡/移除单位时会遇到此问题。

修复：使用 WeakRef 或先保留 Variant 并校验有效性再转换，统一正反索引清理；订阅移除生命周期或明确惰性清理语义。增加 free/queue_free 后查询和注销测试。同 ID 被另一节点替换时，还要移除旧节点反向映射；该场景也已复现 stale id_of。

### R2 [P1] UI/依赖重绑定清空实体表，却没有重新登记存活实体

位置：`game/app/game_director.gd:2139–2140`。

rebind_modules 的既有契约是不重开对局，只替换 HUD/选择器等依赖。新增 clear 会删去全部实体映射，而 UnitsModule.configure 不扫描/重注册单位；注册目前仅发生在 spawn_trained。于是重绑后还活着的训练单位通过 EntityId 查询不到。初始地图单位、召唤等来源也尚未统一登记。

修复：普通重绑定保留注册表；仅对局结束时清空。所有出生/导入/召唤和移除路径归统一生命周期入口。补真实对局测试：生成并取得 ID→替换 HUD/选择器→重绑→身份仍有效；重开后旧 ID 不能误指向新局实体。

### R3 [P1] 同步的共享包缺少依赖闭包和资源路径迁移

位置：`tools/workspace/Sync-Packages.ps1:12–15`、第 38 行。

脚本复制 match/entities/features，但没有复制它们依赖的 game/scripts、scripts/map、shared、定义类型及所需场景，也没有把旧 res:// 路径映射到 addons。packages/map 等目前主要为 README。隔离复制源码并运行原同步脚本、导入目标项目之后，实际 load `res://addons/rts_gameplay/match/game_session.gd` 报缺 `res://game/scripts/logic/melee_victory_rules.gd` 和 PlayerStock 类型。

boot 仅打印并退出，未加载共享运行库，因此 boot 成功无法证明双产品可用。文档已说明是壳，可以保留这种阶段状态；但同步产物还不能作为共享包可加载验证。

修复：建立明确的包依赖/文件清单，迁移或适配内部资源路径及 Autoload；逐包加载入口测试，再验证真实游戏/编辑器启动和导出制品。测试缺少依赖时必须失败，不能以空 boot 代替。

### R4 [P2] content_hash 是目录地址哈希，不是内容版本

位置：`scripts/content/content_registry.gd:41–45`。

哈希仅包含 package_id 和绝对根路径。原位置修改定义/资产，哈希不变；相同内容放到另一台机器的不同路径，哈希反而变化。最小复现已验证：同一包目录下 JSON 从 value=1 改成 2，两次快照 hash 一致。这不能用于缓存失效、内容一致性或发布锁定。

修复：对规范化 manifest、逻辑相对路径、文件内容及影响结果的导入版本生成确定性摘要；或消费经验证的构建清单。补原地内容变化、搬迁路径、文件枚举顺序和基础包内容变化测试。

### R5 [P2] 快照冻结只设置标记，未冻结内容视图

位置：`scripts/content/content_snapshot.gd:6–16`；关联 ContentRegistry.commit_snapshot。

所有字段公开可写，freeze 后 snapshot_id/package_ids 等仍可改，本次已复现。更根本的是快照只记录包 ID/hash，解析仍读取全局可变 AssetProvider：旧快照引用还在时，commit 新包会立即修改共享 overlay 并清空 DefStore，没有对局持有/释放或版本隔离门禁。所谓“冻结对局内容”尚未成立。

修复：将元数据封装为只读访问/防御性副本；快照持有对应版本的解析索引和定义视图。第一阶段可以显式禁止活跃对局换包，切换只在退出后执行。同步处理模型/失败缓存及派生 Catalog，不能只清 DefStore。增加旧快照保持语义不变和活跃对局拒绝换包测试。

### R6 [P2] 请求契约中的玩家与追加标志被静默忽略

位置：`game/scripts/logic/command/command_router.gd:51–84`，字段定义见 CommandRequest。

submit_request 转发 req.units/goal/source，但没有读取 player_id、queue_append。所有权过滤仍使用 Router 绑定玩家，移动仍执行 queue.set_current 并清掉等待订单。调用方显式指定另一玩家或 queue_append=true 时，没有拒绝或执行其语义，可能命令错误归属或意外覆盖队列。已有测试只覆盖空选择/无效目标和类型构造，没有此边界。

修复：玩家身份应来自可信命令上下文，明确拒绝与绑定上下文冲突的 player_id；不要简单相信任意传入玩家号。追加要实现订单调度，未支持前返回明确错误，不能静默当替换。补两玩家、追加保留、拒绝无副作用和实际攻击执行测试。

## 尚未完成的架构能力（区别于已复现缺陷）

- BehaviorRegistry 当前没有真实技能工厂注册/消费调用；Director 的 ensure 方法也未进入正常装配链。现有被动分支仍走原控制器。需要一个真实技能扩展贯通后才算开放扩展点完成。
- ContentRegistry 没有读取/校验 manifest、依赖或冲突，demo_mod 只有清单与说明，尚未包含可加载的覆盖定义。示例测试验证的是登记，不是定义/模型实际被替换。
- 架构门禁主要验证文件存在和若干旧路径；没有覆盖共享层→应用依赖、Autoload 可用性、所有新旧目录和动态引用，不能证明依赖规则已经被执行。
- 新请求只接入玩家部分停止/移动路径，攻击与 AI 等仍有旧入口。保留兼容入口合理，但阶段状态应写为“纵切适配”，而非请求链已经统一。
- 双应用无真实对局/地图编辑入口验收、无独立导出制品验证，D4 仍是壳阶段；不建议据当前通过的单元测试开始删除根工程。
